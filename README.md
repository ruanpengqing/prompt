# Prompt 提示词库

整理自 [sqlyouran/first](https://github.com/sqlyouran/first) 的 `openspec/prompt` 目录，是一套 **Spec-Driven Development（规格驱动开发）** 实践提示词集合；已在保留各篇用途与适用范围的前提下，抽象原项目专属信息。

按软件工程生命周期分为 8 个阶段目录，文件名 `编号-总结.md` 保留原始顺序（对应源仓库章节顺序 ch4 → ch16）。

## 使用方式与抽象边界

使用前将 `{{参数名称}}` 替换为当前项目的真实信息。同一参数在同一篇及连续使用的多篇提示词中应保持一致；目录参数填写时不要带末尾 `/`。多段提示词按原顺序分轮使用，后续段落依赖前一轮输出。

- 替换对象：原项目名称、品牌文案、目标用户与地区、团队与预算、现有代码名称与路径、环境地址及登录账号。通用工程流程中的业务模块名称同样属于上下文，例如第 23 篇的“景点模块”应替换为 `{{目标模块}}`，固定规则文件名也应参数化。
- 保留内容：功能类型、技术栈及版本、字段与状态码、认证要求、性能与测试约束、输出格式、执行顺序，以及“只诊断”“先别实现”等行为边界。
- 抽象时区分业务实例与方法约束：通用测试回归流程不绑定景点模块；JWT 测试中的 JWT、submodule 门禁中的子仓场景则决定方法本身，应予以保留。具体业务功能提示词需逐篇判断，避免仅替换项目名便认定抽象完成。
- 指定要新建的类名、字段、路由和输出文件名属于方案本身，予以保留；引用原项目已有代码的位置则使用占位符。提示词中要求的现有状态是使用前提，使用时应先确认当前项目符合。
- 登录账号和密码使用占位符，实际使用时通过安全方式提供，不将真实凭证保存进提示词库。

本次共抽象 29 篇。其余 13 篇没有需要抽象的原项目专属信息，正文逐字保留：**2、3、4、12、13、14、21、25、26、27、29、34、36**。编号、文件名和分类保持原样。

## 核心提示词模式（跨项目可复用）

| 模式 | 代表文件 | 要点 |
|---|---|---|
| ⭐ 只诊断，不改代码 | 9, 35, 37, 38 | 划定 Agent 行为边界，先诊断后修复，防止 AI 一上来就大改 |
| ⭐ 分步修复、逐个验证 | 23 | 修一个 → 跑测试确认 → 再修下一个，禁止一次性全改，控制爆炸半径 |
| ⭐ 规则沉淀 | 6, 15, 38 | 把口头约定变成 rules 文件让 Agent 自动遵循，再定期对账检查漂移 |
| ⭐ 多角色编排 | 24, 27 | product-manager → interaction-agent → opsx:propose 流水线，职责单一 |
| ⭐ Spec 四要素 | 3, 8, 11 | 模块边界 / WHEN-THEN 场景 / 数据结构 / 可勾选验收标准 |
| ⭐ 防幻觉核实 | 42 | AI 的观察先核实再行动，"帮我核实别全信" |
